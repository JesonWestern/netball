## 6. 关于「旧值绝迹 vs 可追溯」的裁定（回答 installer 提出的分歧）

**我的结论：维持「交付物事实性描述中旧值 0 命中」的严格口径，不因可追溯性放宽；但「可追溯」必须由显式指针保障，而不是靠在正文里保留旧值。**

理由与判据（可机检）：

1. **自检串的目的是防「旧值被当成现行事实」**，不是「永不提及」。所以判据应分两层：
   - **事实性断言层**（§1 交付物清单、§2 AC 表、§3 资源表、§4 已知限制）：旧值必须 **0 命中**；
   - **变更记录层**（修订记录、作废声明）：允许出现旧值，但同一条目内必须同时具备「旧 → 新」的显式标记。
2. **installer 的做法正确**：它把作废声明写成「早期构建…**均已作废**，不代表交付物；锚点历史见 `.agent\workflow.md` 与本文件 §7」，并把完整旧 sha 留在 `workflow.md` / `V4-REPORT §0`。**这满足「事实层绝迹 + 指针可追溯」**，而且比在正文里保留完整旧 sha 更安全——正文是全篇最容易被断章取义的地方。
3. **一处需要留意的双标**：`交付说明.md:275`（D-11 修订记录）仍保留 `1.7:1`。按上面的两层判据这是**合规**的（同一条目里明写「改为…1.2:1」），但它与「sha 必须绝迹」看起来矛盾。→ **这不是矛盾，是分层**：sha 是**锚点**（一旦出现就会被当作可复制的现行值），`1.7:1` 是**被替换的旧文案**（出现即自带「旧」语义）。建议把这条分层规则写进自检脚本注释，否则下一轮可能有人为了「绝迹」把修订记录也删掉，反而丢历史。
4. **因此我不要求 installer 回退**：现状（4 位前缀/仅指针）我接受；若将来有人想把完整旧 sha 贴回作废声明，也**允许**——只要它在变更记录层并带「作废」标记。**两层判据同时成立即通过，任一层违规即 FAIL。**
